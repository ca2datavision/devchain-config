# scripts/

Utilities for changing and checking DevChain preset configs. Python 3 standard
library only — no install step, matching the repo's "standard library only"
principle in `docs/development-standards.md`.

| File | Purpose |
|---|---|
| `refresh-models.py` | Rewrite model pins across a preset directory |
| `verify-presets.py` | Check the config invariants; exits non-zero on violation |
| `approved-models.txt` | The model allowlist `verify-presets.py` checks against |

---

## verify-presets.py

```bash
scripts/verify-presets.py                     # all presets at HEAD
scripts/verify-presets.py --ref <commit>      # a specific commit
scripts/verify-presets.py --preset claude-codex-gemini-advanced
scripts/verify-presets.py --dir <path>        # standalone tree, no git
scripts/verify-presets.py --self-test         # prove the checks actually fail
```

Exit codes: `0` all invariants hold · `1` violation(s) found · `2` usage/environment.

Three invariants:

1. **Allowlist** — every `--model` value in every profile appears in
   `approved-models.txt`. Both option syntaxes are recognised (`--model=<id>`
   codex-style and `--model <id>` claude/gemini-style). An allowlist rather
   than a denylist, because a denylist of retired IDs cannot catch a typo'd or
   newly-invented one.
2. **No dangling pins** — every agent `providerConfigName` resolves via
   `agent.profileId` → `profile.id` → `profile.providerConfigs[].name`.
   Agents have **no `profileName` field**; keying on one produces a false
   DANGLING verdict on clean work.
3. **Round-trip, sources → artifact** — composing `teams/<preset>/` reproduces
   the committed `teams/<preset>.json` byte-for-byte.

### Why the round-trip direction matters

"Round-trip" names two different guarantees, and only one is useful here:

- *artifact → artifact* (decompose the composed JSON, recompose it) proves only
  self-consistency. It never reads the tracked source directory, so a composed
  file hand-edited away from its sources **passes**.
- *sources → artifact* (compose from `teams/<preset>/`, compare to the committed
  JSON) is the direction that catches that drift. This is what the script does.

### Safety

Verification **never mutates the tracked tree**. `compose.py` writes
`<dir>.json` in place, so an in-tree "read-only" check would rewrite the repo.
Everything runs against a throwaway copy materialised with `git archive`.

> **Do not use `decompose.py` in a checker.** It computes
> `out_dir = json_path.parent / json_path.stem` and `shutil.rmtree`s it, so
> pointing it at `teams/<preset>.json` **deletes the tracked source directory**.

### The self-test

`--self-test` copies a preset to a temp dir, seeds one violation per class, and
asserts each is caught **by the specific check that targets it** — not merely
that some violation fired. That distinction is load-bearing: mutating a source
file also perturbs the composed artifact, so round-trip alone reports a
violation for every seeded case. A weaker assertion would stay green with the
allowlist and dangling-pin checks reduced to no-ops.

Verified by mutation: neutering any one check turns the self-test red and names
the broken check. A checker that passes everything is indistinguishable from a
checker that checks nothing.

## refresh-models.py

```bash
# dry run (default) -- prints what would change, touches nothing
scripts/refresh-models.py teams/<preset> --rule gpt-5.2=gpt-5.6-terra

# apply, and record new IDs in approved-models.txt
scripts/refresh-models.py teams/<preset> --rule OLD=NEW --apply --epic <ref>

# many rules from a file (OLD=NEW per line, # comments allowed)
scripts/refresh-models.py teams/<preset> --rules-file rules.txt --apply
```

Then regenerate and check:

```bash
python3 compose.py teams/<preset>
scripts/verify-presets.py
```

The script only edits `profiles/*.json` and `agents/*.json`. It never writes the
composed `<preset>.json` — that is generated by `compose.py`.

### Two properties that are not obvious

Both were rediscovered independently by two agents during the Phase 1 model
refresh, which is why they are written down rather than left to be rediscovered
a third time.

1. **Single-pass alternation.** All rules compile into one alternation applied
   in a single `re.sub` pass, so each source position is rewritten at most once.
   A sequential chain lets a later rule re-match an earlier rule's output — that
   is what produces `gemini-3.1-pro-preview-preview`.
2. **Raw-text editing, never `json.load`/`dump`.** `providerConfigs` entries are
   hand-maintained single-line JSON objects; a load/dump round-trip reflows them
   and breaks byte-identity with the committed composed JSON.

### The boundary rule

- A **trailing** boundary is required — `claude-opus-4-5(?![A-Za-z0-9._-])`.
  It gives exact-boundary matching (`gpt-5.2` never matches inside `gpt-5.25`)
  and, for free, cross-run **idempotency** when a rule extends its own input as
  a prefix: on a second run `gemini-3.1-pro-preview` is not matched by
  `gemini-3.1-pro`, because the next character `-` is in the boundary class.
- A **leading** boundary must **not** be required. Config names embed the model
  ID as a suffix (`default-claude-opus-4-5`), so the match is preceded by `-`.
  Requiring a leading boundary would silently skip every config rename — which
  is precisely the rename the refresh exists to perform.

## approved-models.txt

One model ID per line; blank lines and `#` comments ignored. `--apply` adds new
IDs and drops retired ones automatically.

**Before adding an ID, smoke-test it against its CLI.** Note the CLI trust
guards — the obvious invocations do not run as written in this environment:

```bash
claude --model <id> -p "say ok"
codex exec --skip-git-repo-check -m <id> "say ok" < /dev/null
gemini --skip-trust -m <id> -p "say ok" < /dev/null
```

Pass/fail semantics: `404`/unknown-model = **FAIL, do not add** · `2xx` = **PASS** ·
`429`/quota = **PASS**. A 429 is a pass because model validation happens *before*
the quota gate — a bogus ID returns 404 and never reaches quota, so a 429 proves
the ID resolves.
