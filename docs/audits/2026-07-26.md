### 429 semantics verified this run, not assumed

Control probe with a deliberately bogus ID:

```
gemini --skip-trust -m gemini-9.9-bogus-audit -p "say ok" < /dev/null
→ ModelNotFoundError, code: 404
```

A bogus ID returns **404**, not 429 — so model validation precedes the quota
gate and the two 429s above are positive evidence the IDs resolve. Per the
runbook this control must be re-run whenever the semantics are questioned; if it
ever returns 429, every VALID-but-blocked verdict here must be re-examined.

**Note on the `gemini-3.1-pro-preview` echo:** its quota error names
`model: gemini-3.1-pro`. That is server-side normalisation to the model family
for quota accounting, not evidence the alias resolves to the retired ID — an
unresolvable ID 404s before reaching quota, as the control demonstrates. Same
observation as Phase 1's gate; recorded so it is not re-litigated.

### ⚠️ Finding: documentation presence does not prove availability

Discovered while cross-checking, and now recorded in the runbook because it
changes how future audits must read Step 2:

| ID | In official docs | Live status |
|---|---|---|
| `gemini-3.1-pro` (retired) | **still present**, 1 bare occurrence | **404 — withdrawn** |
| `claude-opus-4-5` (retired) | **still present**, ×4 | superseded |
| `claude-opus-4-7` (retired) | **still present**, ×4 | superseded |

Retired models linger in deprecation and legacy tables. A documentation hit
therefore **cannot clear** a model that fails the CLI check. This is not a
defect in any pin — all six current pins pass both checks — but it means Step 2
is a leading indicator of *announced* deprecation, never a substitute for
Step 1. Had this audit relied on documentation alone, `gemini-3.1-pro` would
have read as healthy on the very day it was returning 404.
