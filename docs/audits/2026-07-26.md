gate and the two 429s above are positive evidence the IDs resolve. Per the
runbook this control must be re-run whenever the semantics are questioned; if it
ever returns 429, every VALID-but-blocked verdict here must be re-examined.

| **OpenAI** | **removed** | retired `gpt-5.2` and `gpt-5.5` → **0** boundary matches |
| **Anthropic** | **retained**, under an explicit **"Legacy models"** heading | `claude-opus-4-5` ×2 and `claude-opus-4-7` ×4, in the page's embedded JSON (incl. the versioned `claude-opus-4-5@20251101`) |

So a documentation hit means **different things per provider**:

- **Google / OpenAI** — the list tracks current availability, so absence is
  meaningful and presence is reasonable evidence a model is current.
- **Anthropic** — presence proves nothing on its own; a superseded model stays
  listed. What matters is *which section* it sits in.

Step 1 remains the stronger signal, and a Step 1 / Step 2 disagreement is a
finding to investigate rather than average out. But note this **strengthens**
the user's documentation-based ruling for Gemini: because Google removes
withdrawn models, a boundary-correct doc check gives Gemini a genuine
availability signal — `gemini-3.1-pro` is absent, which is the correct reading
for a withdrawn model.

None of this indicates a defect in any current pin: all six pass both checks.

## ⚠️ Correction notice — this file was revised after review

**The first version of this audit reported a false positive**, caught in review.
It is recorded rather than quietly overwritten, because the failure mode is
instructive and the runbook now guards against it.

**What was wrong.** The documentation cross-check used substring matching
(`grep -F`). It reported *"`gemini-3.1-pro` still present in the canonical
Gemini docs, 1 bare occurrence"* and built the headline finding on that —
concluding that documentation alone would have read the withdrawn model as
healthy.

**What is actually true.** `gemini-3.1-pro` is a strict prefix of
`gemini-3.1-pro-preview`, the project's signature trap. Boundary-matched, the
retired ID has exactly **one** occurrence in the page, and reading it shows it
is an HTML heading anchor — `id="gemini-3.1-pro"`, slugified from the visible
heading "Gemini 3.1 Pro" — **not a model-identifier listing**. Google has
removed the model. The original conclusion was therefore **inverted**:
documentation-based validation for Gemini is *stronger* than that version
claimed, not weaker.

**Two distinct defects, only one of which was the prefix trap:**

1. **Substring matching** — fixed by the boundary rule the repo already uses in
   `scripts/refresh-models.py`. Every count in this file was re-derived with it;
   four of six changed (`claude-fable-5` 21→11, `gpt-5.6-terra` 4→3,
   `gpt-5.6-sol` 4→3, `gemini-2.5-pro` 5→2).
2. **Counting markup rather than listings** — boundary matching alone does *not*
   fix this. Even a correct count over raw HTML picks up heading anchors, URL
   slugs, vendor-prefixed forms (`anthropic.claude-opus-5`) and embedded JSON
   payloads. The runbook now says the number is a triage signal and that a
   non-zero result must be confirmed by reading the rendered page.

**What survived unchanged:** every CLI verdict, the 429 control probe, the
allowlist comparison, the ledger, and the SOURCE UNAVAILABLE handling. The
Anthropic half of the original finding was correct and verified — retired
`claude-opus-4-5` and `claude-opus-4-7` genuinely are still listed, under an
explicit "Legacy models" heading. The finding was reframed onto that evidence,
which turned out to be the more useful version: **providers differ**.

**The lesson worth keeping.** The original write-up filed a concern reading
*"documentation matching is substring-based on fetched HTML"* — correctly
naming the defect — while presenting a headline finding that the same defect had
already produced two sections above. Identifying a weakness in a method is not
the same as checking whether it has already fired.
